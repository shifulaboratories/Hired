The stage values, in order:

`WISHLIST` · `APPLIED` · `INTERVIEWING` · `OFFER` · `ACCEPTED` · `LOST`

Six, and that is deliberate. A recruiter screen, a technical round and a final were three
columns for one thing — talking to them — and which one a given employer's process belonged
in was a guess that changed by employer. They are one `INTERVIEWING` stage, and how deep it
got is `interviewRound`, a number you pass to `move_application_stage`.

The activity types:

`NOTE` · `STAGE_CHANGE` · `EMAIL_SENT` · `EMAIL_RECEIVED` · `CALL` · `INTERVIEW` ·
`FOLLOW_UP` · `APPLIED` · `OFFER` · `REJECTION` · `REFERRAL` · `OUTREACH`

<Note>
  Everything that did not work out is `LOST`, and **why** is a LOSS tag you pass as
  `lossReasons` — "Rejected", "Ghosted", "Withdrew", "Declined their offer", or the
  person's own words. Say which. The funnel counts a decision against somebody and a
  non-response differently, and the advice that falls out of those is different; silence is
  the most common ending, and filing it as a rejection makes the funnel lie.
</Note>

Three tools answer "what is due", and the difference matters: `list_follow_ups` is what is
already overdue, `list_schedule` is a whole window of dated work merged together, and
`list_tasks` is to-dos regardless of date.

### `pipeline_stats`

_Pipeline stats_

Counts by stage, applications in flight, sent this week, interviewing and the deepest round reached, offers, open tasks, follow-ups due and response rate. Start here for any 'how is my search going' question. `active` counts applications actually sent and still alive — wishlist rows are not in it. `responseRate` counts an application by how far it ever got, so an interview then a rejection is a response. `responseRateBasis` is how many applications the rate rests on: under about ten it describes luck, so say the counts rather than quoting a percentage at somebody who has applied to three things.

No arguments.

### `list_applications`

_List applications_

List job applications, one summary row each — no posting text, notes cut to a line with their full length in notesChars; get_application returns the whole record. Closed ones (ACCEPTED and LOST) are excluded by default. Two numbers answer different questions: daysInStage is time since the last stage change; quietDays is time since ANYTHING happened — a call, an email, a stage move — counted from lastTouchAt. 'What has gone quiet' is quietDays, and quietForDays returns only those past it — the fastest answer to 'what needs chasing'. Capped at 100 rows unless you raise `limit`, and a cut-off result says how many there were before the data, so narrow the filters rather than reporting a short list as everything.

| Argument | Type | |
| --- | --- | --- |
| `stage` | enum | Only this stage  `WISHLIST` · `APPLIED` · `INTERVIEWING` · `OFFER` · `ACCEPTED` · `LOST` |
| `includeClosed` | boolean | Include accepted / rejected / withdrawn |
| `search` | string | Filter by company, role title or notes |
| `quietForDays` | number | Only those with no activity for at least this many days |
| `limit` | number | Max rows to return. Default 100, hard ceiling 500. Prefer narrowing the filters. |

### `capture_job_posting`

_Capture job postings from their URLs_

The FIRST tool to call when someone shares a link to a job posting — or twenty, from a morning of open tabs. Pass `url` for one or `urls` for several. Fetches each page server-side and creates the application in one move, on the wishlist: company matched or created, role title, full description, location, compensation and source filled; a company already on file only has its empty fields filled. THE SAME ROLE IS NEVER CREATED TWICE: a live application with the same employer and title comes back as a duplicate naming that row, within a list too. When a page does not state the employer or the role readably, nothing is created and whatever WAS parsed comes back — show it, ask for the missing pieces, and use create_application. Never guess an employer from a URL. With `url`: returns captured true and the application, or captured false with `duplicate` or a reason. With `urls`: three lists — captured, duplicates and failed — with every URL in exactly one; report all three, not a count. If they already applied, follow with move_application_stage.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `url` | string | One posting's URL, e.g. a Greenhouse, Lever, Ashby, Workday or LinkedIn job link |
| `urls` | string[] | Several postings' URLs. Duplicates within the list are collapsed before anything is fetched. |

### `watch_company_board`

_Watch a company's jobs board_

Watch one employer's own jobs board and hear when a matching role appears — the tool for 'tell me when Stripe posts a staff engineer role'. Reads Greenhouse, Lever and Ashby: pass the board link or the company's careers page, and an embedded board is followed through. ANY OTHER BOARD IS REFUSED and nothing is saved — for Workday, SmartRecruiters or a hand-built page, browse it and paste links into capture_job_posting. THE FIRST LOOK PROPOSES NOTHING: what is on the board today is recorded as already seen, unless propose_existing queues the first ten matches. After that, each new matching role becomes a proposal on their dashboard, posting already read, to accept onto the wishlist or dismiss. NOTHING REACHES THE PIPELINE WITHOUT A YES. Returns the watch, the provider and how many roles the board carries today — read that number back, since a big board with no filters is a noisy watch. Calling again for the same board changes its filters rather than adding a watch. A `scheduleNote` means nothing on this instance checks watched boards on a schedule yet — say so, because a watch nobody runs hears about nothing.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `board_url` | string | **required** — The board or careers page — boards.greenhouse.io/acme, jobs.lever.co/acme, jobs.ashbyhq.com/acme, or acme.com/careers |
| `company_id` | string | The company on file this board belongs to, from list_companies. Preferred |
| `company` | string | Their name, when there is no id yet. Matched against the companies on file before anything is created |
| `title_terms` | string[] | A role's title has to contain ANY of these, case-insensitively, e.g. ['staff engineer', 'principal engineer']. Empty means every role on the board |
| `location_terms` | string[] | AND its location or work mode has to contain ANY of these, e.g. ['remote', 'new york']. Empty means anywhere |
| `propose_existing` | boolean | Queue up to ten roles already on the board as well. Default false, which makes the first look a baseline |

### `list_company_watches`

_Which boards are being watched_

Every company board this person is watching: the employer, which provider it reads, the title and location filters on it, when it was last looked at, how many roles it has proposed, and anything that went wrong the last time. Call it before adding a watch, so you change the filters on the one that already exists instead of making a second. It is also the answer to "why have I not heard anything about Acme" — a watch carrying `lastError` has been failing quietly, and one with a `lastFoundAt` of never almost always has filters narrower than the board's own wording. Read-only.

No arguments.

### `update_company_watch`

_Change a board watch's filters_

Change what a watch is looking for, or park it without losing what it has already seen. `title_terms` and `location_terms` REPLACE the lists they are given — send the whole list, not the one term being added, and call list_company_watches first to see what is on there. Widening the filters does not re-offer roles the watch has already decided about: everything on the board the first time it looked is marked seen for good, so a wider filter finds new postings rather than old ones. Setting enabled false keeps the row and stops the looking, which is what somebody wants during a heavy month; unwatch_company_board is for being done with it.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Watch id, from list_company_watches |
| `title_terms` | string[] | Replaces the title filter. An empty list means every role |
| `location_terms` | string[] | Replaces the location filter. An empty list means anywhere |
| `enabled` | boolean | False parks it without deleting it |

### `unwatch_company_board`

_Stop watching a company's board_

Stop watching a board. The watch is deleted outright — there is no archive for one, and this cannot be undone; watching the same board again starts from a fresh baseline, so nothing already on it will be offered. Proposals it has already queued are left exactly where they are, for them to accept or dismiss, and nothing else about the company, its applications or its people is touched. Say whose board you are about to stop watching before you call it.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Watch id, from list_company_watches |

### `check_company_board`

_Look at a watched board now_

Read a watched board now instead of waiting for the schedule, and queue anything new — the tool for 'anything new at Acme?'. It matches the filters against roles the watch has not yet decided about and queues up to ten as proposals, posting read into each. NOTHING REACHES THE PIPELINE: roles wait in the review queue, and accept_proposal creates the application — never follow this with accept_proposal unless the person said yes to that role. Returns how many roles the board carries, how many matched, were queued, and were skipped as already seen. With no id it checks every watch, least recently checked first, a few seconds apart. An instance with /api/sweep/<token> on a schedule does this unasked; this jumps the queue.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | One watch, from list_company_watches. Omit to check them all |
| `limit` | number | How many watches to check when no id is given. Default 20 |

### `check_posting_live`

_Check whether a posting is still up_

Fetch the posting behind an application and report whether it is still up — a 404 is usually the first sign a role was filled or pulled, weeks before anybody writes. Pass application_id for one, or nothing to work through the open applications with a link, least recently checked first. THIS NEVER MOVES A STAGE AND NEVER LOGS TO A TIMELINE: it records the posting's state on the application — LIVE, GONE, UNCLEAR or UNREACHABLE, with the date and what the host said — and stops. GONE needs TWO 404s a day apart; a single one reads UNCLEAR, as does a page that answers without naming a role, which client-rendered boards do whether the job exists or not. UNREACHABLE says nothing about the role. Returns a line per application and how many are gone. When something is GONE, tell them plainly and offer log_activity or ask where it stands — do not decide for them, and do not call move_application_stage off the back of this.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | One application. Omit to work through the open ones |
| `limit` | number | How many applications to check when no id is given. Default 25 |
| `force` | boolean | Check even one looked at in the last three days. Use when they are asking about a specific job right now |

### `record_offer`

_Record an offer_

Save what somebody actually offered: base, bonus, equity, sign-on, terms in words, and the date they must answer by. Call it the moment a number is said out loud, even a verbal one. EVERY CALL WRITES A NEW VERSION rather than replacing the last: when they come back with more, call this again, and the rows become the negotiation record. update_offer is only for fixing a typo. Amounts are WHOLE UNITS — 215000, and '215k' is understood; equity is the yearly value where they stated one, with the schedule in vesting. Never invent a number: if they said 'competitive', record nothing and say the base is still unknown. This does NOT move the application to the offer stage; check the stage that comes back and call move_application_stage if it is behind. respond_by is what puts the deadline in their notifications.

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | **required** — Which application this offer is for |
| `base_amount` | number | Annual base salary, whole units, e.g. 215000 |
| `bonus_amount` | number | Target annual bonus in the same units. Omit when none was stated |
| `equity_amount` | number | Yearly value of the equity grant where they stated one. Leave out when they only described a percentage — put that in terms |
| `sign_on_amount` | number | One-off signing bonus |
| `currency` | string | Three-letter code, e.g. USD, GBP, EUR. Defaults to USD |
| `terms` | string | Everything the numbers cannot hold, in their words: '0.4% over four years, one year cliff', 'relocation on top', 'review at six months' |
| `vesting` | string | The vesting schedule, e.g. '4 years, 1 year cliff, monthly after' |
| `received_at` | string | The day it was put on the table, YYYY-MM-DD. Defaults to today |
| `respond_by` | string | The day they need an answer, YYYY-MM-DD. This is what the notification bell reads |
| `starts_on` | string | Proposed start date, YYYY-MM-DD |

### `list_offers`

_List offers_

Every offer on file, newest first, each with the application and company it belongs to. Several rows for one application are its versions, not several offers — the first one recorded is the opening number and the newest is where it stands now. Pass application_id for one job's history, or live_only to drop the ones that came to nothing. For a side-by-side of what is actually on the table, compare_offers is the better tool; for arguing one of them, offer_briefing. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | Only this application's offers — every version of it, newest first |
| `live_only` | boolean | Drop offers whose application was lost. An accepted one stays — it is the one they took |
| `limit` | number | Max rows to return. Default 50, hard ceiling 500. Prefer narrowing the filters. |

| `currency` | string | Three-letter code, e.g. USD |

| `vesting` | string | The vesting schedule. Replaces what is there |
| `received_at` | string | The day it was put on the table, YYYY-MM-DD |

Say what will go and get a plain yes first.

### `get_outbound_settings`

_Can this workspace send mail_

Whether this app is allowed to send a message from this person's own mailbox, how many a day they set, whether each one waits for a click, which mailboxes can actually send, how many have gone today and what is standing in the way right now. `blockedBecause` is the whole answer when it is non-empty — read it back rather than trying the send and reporting a failure. Three separate things have to be true: an admin turned it on for the instance, the person set a daily number above zero themselves, and a Google or Microsoft mailbox is connected WITH the send permission (an IMAP account cannot send at all, whatever else it does). Read-only, and it sends nothing.

No arguments.

### `draft_outbound_email`

_Draft a message to send from their own mailbox_

Write a message and put it in the outbox as a DRAFT. IT IS NOT SENT — nothing here sends anything; send_outbound_email is a separate call with its own refusals. For the follow-up nobody gets round to: the chase after a week of silence, the thank-you after an interview, the reply to a recruiter. It goes from ONE OF THEIR OWN MAILBOXES, so it arrives from them. IT CAN ONLY GO TO SOMEBODY ALREADY ON FILE: pass contact_id and the address is read off their record — no argument takes an address. To mail somebody new, create the contact first and say so. Write in THEIR voice from what is on file — call prep_letter or search_me first for anything substantial — and never invent a meeting, a name, a date, a number or an agreement. Keep it short; create_letter is for anything that wants a title and a draft history. Returns the draft id, the mailbox it will go from, what it says, and whether it needs approving: by default every message waits for a click in the app that NO TOOL CAN MAKE, and the result says so.

| Argument | Type | |
| --- | --- | --- |
| `contact_id` | string | **required** — Who it is to. The address comes off their record — there is no way to pass one |
| `subject` | string | **required** — The subject line |
| `body` | string | **required** — The message, plain text, in their voice |
| `account_id` | string | Which of their mailboxes to send from. Omit to use the only one that can send |
| `application_id` | string | The job this is about, so the send lands on that job's timeline |
| `letter_id` | string | A letter this was drafted from, if there is one. Its sentAt is stamped when this goes |

### `list_outbound`

_What is in the outbox_

Every message this app has drafted, sent, failed or had cancelled for this person, newest first — with what it said, who it went to, which mailbox it went from, which connection drafted it and which sent it. Pass status to narrow it: DRAFT is waiting, APPROVED has been clicked and is ready, SENT has gone, FAILED says why in `error`, CANCELLED was called off. Reach for it before drafting anything, so you do not send a second chase to somebody who was chased on Tuesday, and read what went before to match how they actually write. The body is kept after sending, deliberately: a record of what you said is the thing this product exists to keep. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `status` | enum | DRAFT, APPROVED, SENT, FAILED or CANCELLED. Omit for all of them  `DRAFT` · `APPROVED` · `SENT` · `FAILED` · `CANCELLED` |
| `application_id` | string | Only messages about this job |
| `contact_id` | string | Only messages to this person |
| `limit` | number | Max rows to return. Default 50, hard ceiling 500. Prefer narrowing the filters. |

### `send_outbound_email`

_Send a drafted message_

Actually send a draft, from the person's own mailbox. THIS IS THE ONE THING IN THIS APP THAT PUTS A MESSAGE IN FRONT OF SOMEBODY OTHER THAN ITS OWNER. It refuses, by name, when: the instance does not allow members to send; they have not turned sending on and set a daily number; no mailbox can send; they are at their daily limit; one went less than a minute ago; the person or job is archived; or they are in "approve each one" mode and have not clicked approve — a click NO TOOL CAN MAKE, this one included. A refusal is `sent` false with a `reason` to read out; it is not an error and not something to work around. On success it stamps the source letter as sent, writes an EMAIL_SENT activity on the job's timeline, and returns the provider's message id. AN EMAIL CANNOT BE UNSENT: say who it goes to, from which mailbox and what it says, and get a plain yes every time — even in trusted mode. Never send a draft the person has not seen.

**Overwrites or deletes.** **Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Draft id, from draft_outbound_email or list_outbound |

### `cancel_outbound_email`

_Call off a drafted message_

Mark a draft, an approved message or a failed one as cancelled so it can never go. Reach for it when they change their mind, when a draft is wrong enough to rewrite from scratch, or when a failed send should not be retried. The row stays with everything it said — nothing here deletes the record — and a cancelled message cannot be un-cancelled, so draft a new one instead. It does nothing to a message that has already gone, because nothing can.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Message id, from list_outbound |

### `attach_file`

_Keep a file against a job, a person or an offer_

Store a file against exactly one thing: an application, an offer, a letter, a person or a company — the signed offer letter, the take-home they submitted, a recruiter's PDF, a screenshot of a posting since taken down. Pass exactly one of application_id, offer_id, letter_id, contact_id or company_id; there is no way to store a file loose, and nothing in the archive can take one. Send the bytes as `data_uri` when you hold them, or `url` for an https link the server fetches — MUCH cheaper, and the one to prefer when the file is on the web. Default limits are 8MB a file and 250MB a workspace; over either it refuses and says how much is in use. Accepts PDFs, images, plain text, markdown, CSV, JSON, zips and Word or Excel files, and THE TYPE IS READ FROM THE FILE'S OWN BYTES, not its name. The same bytes twice return the first row with `reused` true, so retrying after a timeout is safe. Returns the file's id, size, space in use and a download link that opens in their signed-in browser and is not public. IT NEVER RETURNS THE BYTES; read_attachment reads a text file.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `filename` | string | **required** — What the file is called, e.g. 'northwind-offer-signed.pdf' |
| `data_uri` | string | The file inline: 'data:application/pdf;base64,…'. Use url instead where you can |
| `url` | string | An https link the server fetches. Cheaper than sending the bytes |
| `caption` | string | One line about what it is, in their words: 'the offer as signed' |
| `application_id` | string | The job it belongs to |
| `offer_id` | string | The offer it belongs to |
| `letter_id` | string | The letter it went out with |
| `contact_id` | string | The person it came from |
| `company_id` | string | The company it is about |

### `list_attachments`

_List kept files_

Every file kept in this workspace, or just the ones hanging off one thing — pass application_id, offer_id, letter_id, contact_id or company_id to narrow it. | `letter_id` | string | Only files on this letter |

| `company_id` | string | Only files on this company |

### `read_attachment`

_Read a kept file_

The TEXT of a kept file, for when you actually have to read one — a take-home brief they saved as markdown, a CSV of interview questions, a JSON export somebody sent. Long files are cut and `truncated` says so. Read-only — this never changes the file or the record it hangs off.

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Attachment id, from list_attachments |
| `limit` | number | How many characters of text to return. Default 40,000, which is the ceiling too |

### `compare_offers`

_Compare the offers on the table_

Every live offer side by side: one column per job with its newest version, sorted by what year one actually pays. Each column has base, bonus, equity, sign-on, yearlyTotal (sign-on excluded), firstYearTotal (sign-on included), the deadline and days left, how many revisions, and `leads` naming the lines it wins outright. IT WILL NOT CONVERT CURRENCIES: across currencies `comparable` is false with the reason and nothing leads — say so and ask which currency they want rather than picking a rate. Report terms and vesting alongside the numbers; a shorter cliff or a real start date can outweigh a bigger base. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `application_ids` | string[] | Only these applications. Omit for everything still on the table |
| `include_lost` | boolean | Also include offers from applications that ended in a loss, for a historical comparison |

### `offer_briefing`

_Everything on file for one negotiation_

Call this BEFORE helping somebody answer or negotiate an offer. One read gathers every version of the offer; `advertised`, what the POSTING claimed, which is not what anybody offered; `saidDuringProcess`, timeline lines where money came up, each with its activity id; `pastPay`, what they have written in Me about their earnings; and `competing`, the other offers on the table. `missing` names what is not on file — an unrecorded base, a vesting schedule, a deadline. Quote the evidence back; never state a number that is not in this result, and never pass off a guessed market rate as their data. Read-only, saves nothing.

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | **required** — Which application to brief on |

### `prep_interview`

_Gather everything before an interview_

Call this FIRST whenever somebody has an interview coming up, asks what to expect, or asks you to run prep. One read returns `application` (posting, stage, last ten logged events), `company` research, `interviewers`, `history` (earlier rounds here and how each went), `employerQuestions` (what THIS employer already asked — read these out first), `commonQuestions`, `weakAnswers` (unanswered or rated badly — the homework), `tasks` from the stage checklist, and `missing`: what is not on file. Say the gaps out loud, and NEVER invent a story, an employer, a date or a metric to fill one — if it is not in the result, it does not go in an answer. Hand back the three things this employer cares about most, the strongest TRUE story for each with its real numbers, likely questions and weak spots to rehearse, questions to ask them, and any follow-up the timeline says is owed. Pass interview_id for a booked round, or application_id when no date is set. Read-only, saves nothing.

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | The job to prep for. Enough on its own. |
| `interview_id` | string | A booked round, from list_interviews. Narrows the prep to its format and its interviewers. |

### `schedule_interview`

_Put an interview round on the record_

Record a round of interviews — booked, or one that happened and was never written down. Reach for it the moment a date is agreed. Leave `round` out and it continues from the deepest round on file. The chase clock, per stage. ### `complete_task`

_Complete or reopen a task_

Mark a task done, or reopen it with done: false. When the task repeats, completing it also creates the NEXT instance and returns it as `next` — one, never one per missed week. Reopening and completing again does not make a second: the new instance points back at the one that made it, so the duplicate is refused rather than written.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Task id |
| `done` | boolean | Default true |

### `update_task`

_Update a task_

Reword a task, move its due date, or hook it to something different. Only the fields you pass change; each REPLACES what was there. Pass an empty string for dueAt to clear the date, or for any of the subject ids to unhook it. Setting one subject CLEARS the others, because a task is about at most one thing — so moving a task from an application to a person is one call with contactId, not two. Use complete_task to tick it off; done is not settable here. THE TRAP with repeats: moving this instance's due date moves THIS instance, not the series, because every future date is stepped from the first one. Sending repeat_unit as an empty string stops the series, and completing the task is then the end of it — which is the whole off switch and is on the row somebody is already looking at.

### `export_csv`

_Export a list as CSV_

One of the three lists as CSV text you can hand straight to somebody. 'companies' and 'contacts' take the same filters as list_companies and list_contacts, so narrow it there first and pass the same arguments here. 'applications' takes the pipeline's own filters through `query`, the string the app puts in its URL. Every export ALWAYS includes closed applications. `ids` INTERSECTS with the other arguments rather than replacing them, so send it alone unless you mean 'these rows, and only those that also match'. Archived records are never included; list_archive has those. Read-only: it writes nothing.

### `list_field_values`

_Locations and work modes already in use_

Every location and every work mode already on one of this person's live applications, most-used first with a count each. Call it BEFORE writing either field on create_application or update_application: both are free text and always will be — 'Remote (US, PST overlap)' is a real answer no list survives — but writing 'remote' next to an existing 'Remote' leaves two values that never group together, and this is the cheap way not to. Match case-insensitively against what comes back and reuse that spelling; a genuinely new value is still just a string, so send it. Archived applications do not contribute. Read-only.
