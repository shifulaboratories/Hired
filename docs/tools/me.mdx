Everything the user has written about their own career. `search_me` is almost always
the first call — it is the fastest way in, and it is what an assistant is told to reach
for before writing anything.

<Warning>
  `update_role` with a `background` **replaces** the entire thing. When somebody tells you
  something new about a job already on file, the correct tool is
  `append_role_background`. That tool exists precisely because the update one was eating
  people's notes.
</Warning>

If you already have a resume, you do not have to type any of this. Paste it to your
assistant and ask it to import: one `import_resume` call files the whole document — roles
with their bullets, education, skills, contact details. It only ever adds, so anything
already on file is skipped rather than overwritten, and running it twice is safe.

### `search_me`

_Search Me_

Ranked full-text search across everything the user has written about themselves: role backgrounds, highlights, notes, projects and their profile. This is the FIRST tool to call when tailoring a resume or answering a question about their experience. Words match by stem ('managing' finds 'managed') and terms are ORed and ranked, so search the language of the POSTING, and search two or three times with different words before concluding they have no evidence for something. Returns an excerpt centred on each match with its id and kind, and `use`: only a hit whose use is "evidence" may reach a document. "rules" binds you without being quoted, "caveats" is their positioning note — context, never document material — and "open" is an unsettled fact, so ask. The profile's own background is not searched; get_me_snapshot with only "profile" has it. An empty query returns their roles, newest first.

| Argument | Type | |
| --- | --- | --- |
| `query` | string | **required** — Keywords to search for, e.g. 'kubernetes cost savings' or 'led a team' |
| `limit` | number | Max results (default 25) |

### `get_me_snapshot`

_Get everything in Me_

EVERYTHING in Me at once: profile, every role with its full background, highlights, education, projects, skills, certifications and notes. Use it for complete context, e.g. a resume from scratch; it can be large, so prefer search_me for targeted lookups. `keywordPolicy` says how close to a posting's own words you may write — spelled out in `permits`, beside their transferable skills; read it before drafting. READ `writingRules`, `neverOnADocument` AND `notSettled` BEFORE YOU WRITE ANYTHING; the first and last cover the profile as well as every role. Obey `writingRules` silently. `neverOnADocument` is positioning notes and interview prep — context for you, never on a resume, a letter or anything an employer sees. Never state, round off or pick between `notSettled` facts; if a document needs one, ask. A role with `startUnconfirmed` or `endUnconfirmed` gets the year only for that date. Each role's `resumeEvidence` is the part a document may be written from.

| Argument | Type | |
| --- | --- | --- |
| `include_background` | boolean | Include the full long-form background text for each role (default true). Set false for a lighter payload. |
| `only` | enum | "profile" for the identity block alone: name, headline, contact details, links, summary and their personal background. `hasPhoto` says whether a photo is set (the picture itself is never returned); `timeZone` is the calendar every date here is read against, or empty for the server's clock.  `profile` |

### `set_profile_photo`

_Set the profile photo_

Give the user a headshot, or remove theirs. One picture serves the whole app: their avatar, and the photo on every resume whose design shows one — replacing it here updates them all. Pass `url` for an https JPEG, PNG or WebP already on the web (a GitHub avatar, a personal site), `data_uri` when you hold the bytes, or remove: true to clear it. Over 400KB is refused, so downscale first; a 512px original is plenty. Turning the photo ON for a resume is a separate step: update_resume with showPhoto: true. Never invent a picture of somebody — use only a URL or file the user gave you.

**Overwrites or deletes.** **Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `url` | string | https link to an image to fetch and store |
| `data_uri` | string | The image inline, e.g. 'data:image/jpeg;base64,…' |
| `remove` | boolean | Remove the existing photo |

### `get_role`

_Get a role_

One role in full: its background, that background READ INTO SECTIONS, and all its highlights. `resumeEvidence` is the only part a document may be written from. `rules` bind how this job is described — follow them silently, never quote them. `caveats` are their positioning notes and interview prep: context for YOU, never on a resume, a letter or anything an employer sees. `open` is what they have not settled, an unconfirmed start or end month included — never state, round or choose a version; ask, and settle it with resolve_open_question. When `startUnconfirmed` or `endUnconfirmed` is true, write the year only. `notes` filed against this job are evidence too. `sections` is the whole thing in order, each tagged by kind. Markers are a heading ('## Rules', '## Caveats', '## Open questions', or a shouted suffix like '— INTERVIEW ONLY') or a shouted label opening a line ('NAMING RULE:', '⚠️ OPEN:'); lowercase prose never marks anything, and an unmarked background is all evidence.

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Role id |

### `list_open_questions`

_What they have not settled yet_

Every fact they have marked as not settled: questions in a role's background ('⚠️ OPEN:', '## Open questions'), in their profile's personal background (roleId null), and start or end months marked unconfirmed. Each comes with roleId, role, the question as written and its `kind` — background, start_date or end_date. Reach for it when they ask what is left to tidy in Me, before writing a dated or numbered document, or on 'let's go through my open questions'. Ask them ONE AT A TIME and never answer one yourself. When they answer, call resolve_open_question with the question exactly as it came back. These are already kept off documents, so an empty list means nothing is pending. Read-only.

No arguments.

### `resolve_open_question`

_Settle an open question_

Record their answer to one open question and take the question away. Call it only with an answer THEY gave you in this conversation — never a guess, a rounding or the likelier of two figures. Pass the question exactly as list_open_questions returned it. A marked line inside the background ('- ⚠️ OPEN: $40K or $45K?') is replaced in place by the answer; a line under '## Open questions' is removed and the answer filed as evidence, under `heading` if you give one. An unconfirmed start or end month is settled by passing the month as YYYY-MM (or YYYY if only the year is certain), or no answer to confirm the date on file. Leaving out `answer` on a background question DROPS it. A role's old background stays in its version history, so restore_revision can bring it back; the profile keeps no versions, so a profile question settled stays settled. Returns what was resolved.

| Argument | Type | |
| --- | --- | --- |
| `role_id` | string | The role the question belongs to. Omit for a question in the profile's personal background. |
| `question` | string | **required** — The question exactly as list_open_questions returned it. |
| `answer` | string | Their answer, as a fact written the way it should appear in the background. For a date question, YYYY-MM or YYYY. Omit to drop a question that no longer matters, or to confirm a date as it stands. |
| `heading` | string | Only for a question from an 'Open questions' section: the evidence heading to file the answer under, e.g. 'Scope'. Merges into an existing section of that name. |

### `posting_keywords`

_Where a posting's keywords land_

Read ONE posting on the board and say, term by term, what it lands on: `onFile` with the record that evidences it, `covered` where only a recorded transferable reaches it, `missing` where there is neither. CALL THIS BEFORE TAILORING ANYTHING. Applicant tracking systems screen on exact tokens, so an `onFile` term your draft spells differently is a screen lost over vocabulary; a `covered` term may go in a skills line as comparable if their keyword policy allows. Never move a `covered` term into a bullet about a job, and never invent evidence for a `missing` one — report it as a gap. Terms are ordered by how often the posting repeats them. skills_gap asks the same across every posting, for deciding what to learn; this one decides what goes on the page.

| Argument | Type | |
| --- | --- | --- |
| `application_id` | string | **required** — Application id, from list_applications |

### `append_role_background`

_Append to a role's background_

Safely ADD text to the end of a role's background without touching what is there. The right tool when the user tells you something new about a job on file — and whenever they mention something that went well at their current job (list_roles marks it): a project shipped, a number moved, somebody thanked them. Offer to file it even unasked; Me stops growing the day a search ends. Write it in their words with whatever number they gave, under a month heading like "October 2026"; do NOT polish it into a resume bullet — mine_role_background does that later, with them. A `heading` the background already has merges into that section. Three headings are reserved and change what the text MEANS: "Rules" for a binding instruction on how this job may be described, "Caveats" for positioning and interview prep that must never reach a document, and "Open questions" for a fact they are not sure of yet. Use them when they are telling you a CONSTRAINT, a WORRY or an UNCERTAINTY rather than something they did; everything else is evidence. Once an open question is settled, resolve_open_question files the answer — never rewrite the whole background for it.

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Role id |
| `text` | string | **required** — The new material to append. Markdown welcome. |
| `heading` | string | Optional markdown H2 heading to file it under, e.g. 'Q3 platform migration'. Merges into an existing section of the same name. 'Rules', 'Caveats' and 'Open questions' are reserved — see the description. |

### `delete_role`

_Delete a role_

Destroy a job and everything hanging off it: its background, every highlight drawn from it, and the evidence behind any resume bullet that came from there. There is no archive for a role and no undo — this is not archive_records, which files a company, a person or an application away. Resumes already written keep their text; what they lose is the material that proves it, so trace_resume_evidence will start reporting those bullets as unsupported. Almost nobody means this: a role kept out of a document is a resume edit, not a deletion. Read it back with get_role and get a plain yes first.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Role id |

### `list_highlights`

_List highlights_

Reusable, polished achievement bullets, strongest first. These are the distilled lines you pull from when assembling a resume. Each carries `usedIn`: the resumes that have a bullet saying the same thing (matched by meaning, the way trace_resume_evidence matches, not by exact text), most recently edited first. A strong highlight with an empty `usedIn` is one they have never put in front of anybody — worth offering when tailoring. Capped, and the result says so when it was cut off — pass roleId to narrow it to one job.

### `list_notes`

_List notes_

Free-floating notes not tied to one job: STAR stories, interview prep, references, compensation history. Capped, and the result says when it was cut — except standing rules (kind GUARDRAIL), which are never cut and come first. Each standing rule carries `inBriefing`: whether it fits in the briefing every client reads on connect. A false one still binds but only reaches clients that come here for it, so offer to shorten it or split it into several short rules — create_note with kind GUARDRAIL for each, then update_note to make the original an ordinary NOTE. A note with a `role` is filed against that job. A NOTE whose title reads like a rule ('Guardrails', 'never do X') is NOT a standing rule and reaches nobody unasked — say so and offer update_note with kind GUARDRAIL. For something specific, search_me is better.

| Argument | Type | |
| --- | --- | --- |
| `limit` | number | Max rows to return. Default 100, hard ceiling 500. Prefer narrowing the filters. |
| `role_id` | string | Only the notes filed against this role |

### `import_resume`

_Import a resume into Me_

Turn an existing resume, LinkedIn profile text or any pasted career history into a filled-in Me in ONE call. Reach for this first when the workspace is empty and the user has a document — offer it before asking them to talk through their life. A LinkedIn data-export zip goes to import_linkedin_archive. You do the reading: parse the text into profile, roles with their bullets, education, projects, skills and certifications. Copy what the document says and NEVER invent, upgrade or round anything — no employer, title, date or metric it does not state; a field it is silent on stays absent. Include startDate on every role: two stints at one company import as two only when their dates differ. ADDITIVE and safe to repeat: nothing is overwritten or removed, profile fields fill only where empty, a role already on file (same company, title and start) gains only the bullets it lacks, and a matching education entry, project or certification is skipped. Bullets become highlights. Returns what was created, merged into (with bullets gained) and skipped — report it back. When the workspace is NOT empty, call with dry_run true first: the same report, nothing written. Offer create_base_resume: true, since a resume is usually why they pasted one; it reuses one named 'Base resume'.

| `roles` | object[] | One entry per job in the document, newest first. |

| `projects` | object[] | Side or portfolio projects the document lists. |

### `import_linkedin_archive`

_Import a LinkedIn data export_

Fill in Me from LinkedIn's own data export — the zip from Settings → Data privacy → Get a copy of your data. Reach for this the moment someone says they have one: it needs no interpreting, so it is more accurate than pasting a resume or a profile page. Unzip it yourself and pass each file in `files` with its text EXACTLY as the file has it — do not reformat, summarise or tidy the CSV. It reads Profile, Positions, Education, Skills, Languages, Certifications, Projects and Email Addresses; pass whichever exist, and it names any file it could not use. `jobs` and `connections` are opt-in — offer them, do not assume them. ADDITIVE and safe to re-run, on the same rules as import_resume: nothing is overwritten, and nothing already on file is created twice. ROLES CARRY NO BULLETS: LinkedIn's description is prose, and it lands whole in the role's background rather than being split into achievement lines they never wrote. On a workspace that is not empty, run dry_run true first and read the report back. Returns a ROW COUNT per file — zero on a file that should have rows means LinkedIn renamed a column, so say so — plus what was ignored, created, merged into and skipped. Report that; do not claim success blindly. Never add an employer, title, date or metric that is not in the file.
