"Add this to my work laptop" and "kill the one I pasted in a chat by mistake" are things
you can just say. So is "give me everything you have on me".

## The two emails

Nothing leaves this app unless somebody asked for it. Two messages can:
`set_digest_settings` turns on a Monday summary of where the search stands, a due-today
nudge, or both, and `get_digest_settings` says which are on and whether the instance can
send mail at all.

The nudge sends nothing on a day nothing is due — deliberately, because a daily mail that
says "nothing today" every day is a daily mail people filter, and then the one that
mattered lands in the same folder.

`preview_digest` builds either one and returns it without sending, which is usually the
right tool in a conversation: "what does my week look like" is the same read the mail is
made from. `send_digest_now` actually puts it in their inbox.

<Note>
  Neither is on by default and no admin can turn one on for somebody else. Only offer this
  when a person asks for mail.
</Note>

## Getting it all out

`export_everything` returns a single JSON document holding every record the workspace
owns — Me, resumes, letters, the whole pipeline with its timeline, tasks, offers, tags and
saved views — and `import_everything` puts one back.

The import is **additive and matched by natural key**: a role by employer and title, a
company by name, a job by employer and role. What is already there is left exactly as it
is, so importing the same file twice does nothing the second time and importing into a
workspace someone has already started cannot overwrite it. There is no mode that empties
anything first, deliberately. Run it with `dry_run` first on any file you did not just
write, and read the report back.

<Warning>
  Five things are not in the file, and the export names them: connection tokens and
  mail-account passwords, published `/r` and `/p` slugs, the review queue, anything
  belonging to the instance rather than the person, and the profile photo, which is a data
  URI that would dwarf everything else. A backup people email around must not carry a
  credential or a live public URL.
</Warning>

<Warning>
  `list_connections` deliberately never returns tokens. They are credentials, they would
  sit in a transcript forever, and the only place anyone needs to see one is the client
  they are pasting it into. `create_connection` and `rotate_connection` **do** return one,
  because handing it over is the point of them — treat what comes back like a password.
</Warning>

Prefer `rotate_connection` over `delete_connection` when the client is still in use and
only the URL has leaked: rotating keeps the row and its name, and kills the old address the
moment it returns. It also clears the last-used stamp, and the list is ordered by last use —
so a rotated connection drops to the bottom until the client calls in on the new URL, which
is a useful way to see whether anyone actually pasted it.

### `get_digest_settings`

_Check the two emails this app can send_

Whether this person has asked for a weekly summary or a due-today nudge, what hour they go out at in their own zone, when each was last sent, and whether the instance can send mail at all. `emailConfigured` false means both switches are inert until an admin sets up email — say that rather than turning something on that cannot work. A non-empty `scheduleNote` means nothing calls this instance's digest address on a schedule, so nothing goes out on its own either way: read it back. Read-only.

No arguments.

### `set_digest_settings`

_Turn the weekly summary or the daily nudge on or off_

Turns the three digest emails on or off — all OFF until somebody asks, and this is the only thing that turns them on. Weekly arrives Monday morning with where the search stands. Daily arrives only on a day something is due, and sends nothing on a quiet day. MONTHLY arrives on the last day of the month asking for one thing that went well, so Me keeps growing after the search — offer it the day somebody accepts an offer, which is the day the other two should come off. It stops after three unanswered; logging a win, or switching it off and on, restarts the count. `hour` is in their own time zone. Only offer any of this when somebody asks for mail. Returns the settings as they now stand; a non-empty `scheduleNote` means nothing will send until the instance's scheduler is set up — say so.

| Argument | Type | |
| --- | --- | --- |
| `weekly` | boolean | The Monday summary |
| `daily` | boolean | The due-today nudge. Only sends on a day something is due |
| `monthly_wins` | boolean | The end-of-month ask for one thing that went well. For after the search, not during it. |
| `hour` | number | What hour they go out at, 0-23, in their own zone. Default 8 |

### `preview_digest`

_See what a digest would say_

Build the weekly summary, the due-today nudge or the monthly wins ask and return it WITHOUT sending anything. Reach for it beside set_digest_settings, to show somebody what turning one on would send them. For 'what does my week look like' use list_schedule, and for 'what first today' use morning_brief. Returns the subject, the opening line and the sections. `empty` true on a nudge means nothing is due, and on a wins ask means there is no current role for a win to land on — which is why no mail would go out in either case.

| Argument | Type | |
| --- | --- | --- |
| `kind` | enum | weekly (the Monday summary), nudge (what is due today) or wins (the end-of-month ask). Default weekly.  `weekly` · `nudge` · `wins` |

### `send_digest_now`

_Send one of the two emails now_

Actually send the weekly summary or the daily nudge to this person's own address, immediately, ignoring the schedule and the once-a-day guard. It does NOT ignore the opt-in: somebody who has not turned that message on gets nothing and the result says so. Use it to show someone what they signed up for, or when they ask for their week by mail. For reading it here, preview_digest is the tool — this one puts a message in an inbox.

**Reaches outside this instance.**

| Argument | Type | |
| --- | --- | --- |
| `kind` | enum | weekly, nudge or wins. Default weekly.  `weekly` · `nudge` · `wins` |

### `export_everything`

_Export the whole workspace_

Every record this person owns as one JSON document that import_everything takes back — Me, resumes, letters, the whole pipeline with timeline, tasks, offers, tags and saved views. The answer to 'can I get my data out'. Five things are left out, and the result names them: connection tokens and mail passwords (a backup must never carry a credential), published slugs, the review queue, anything belonging to the instance, and their profile photo. `counts` says how many of each came out — read it back rather than claiming success blindly. If the file is too large to hand around, Settings → Account → Download everything saves the same file from the browser. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `counts_only` | boolean | Return just the counts and what was excluded, with no records. Use it to check what a backup would contain |

### `import_everything`

_Put a workspace export back_

Restore a document written by export_everything. ADDITIVE AND MATCHED BY NATURAL KEY: a role is matched by employer and title, a company by name, a job by employer and role, a tag by kind and name. What is already here is left exactly as it is and only what is missing gets written, so importing the same file twice does nothing the second time and importing into a workspace that already has material cannot overwrite it. It is a restore, not a replacement — there is no mode that empties anything first, deliberately. ALWAYS run it with dry_run true first on a file you did not just write, and read the report back: `created` and `skipped` per area, plus `problems` naming anything that could not be placed. A file from a different version is refused rather than half-read.

| Argument | Type | |
| --- | --- | --- |
| `document` | object | **required** — The whole export document, exactly as export_everything returned it |
| `dry_run` | boolean | Do every lookup and no writes, and report the same numbers. Do this first |

### `whoami`

_Who am I connected as_

The account this connection belongs to — name, email, role, whether it can administer the instance — what this connection is called and what it is served (`connection.scope`), and how far into setup the workspace is. Every other tool acts as this person and can only see their data. Call it when someone new asks what to do first, or when a read comes back empty and you are deciding whether that is an empty account or a wrong query: `setup` says which of the three things a workspace needs (a job on the board, career material in Me, something connected) are done and what each is waiting for. `tourSeenAt` null means they have never been shown around the web app — explain things rather than assuming they know what a pipeline stage is.

No arguments.

### `load_sample_workspace`

_Fill an empty workspace with a sample search_

Write a small, plausible job search into this workspace to look at and practise on: four employers, six applications across every stage including one lost, five people, four weeks of timeline, three tasks (one overdue), two letters, a resume, and an offer revised a week later for eighteen thousand more. Reach for this when somebody says the app looks empty, or when showing how it works before they have anything real — a better first minute than a tour of blank screens. It is ORDINARY DATA, so it moves, filters, exports and archives like their own. It refuses on a workspace that already has jobs, roles or highlights, because a sample mixed into a real search is noise nobody can separate; if they want it anyway, say what it will add and pass allow_anyway true. wipe_sample_workspace removes only what this made, keeping and naming anything they have edited or added to. Returns what was created and where to look first.

| Argument | Type | |
| --- | --- | --- |
| `allow_anyway` | boolean | Load it even though this workspace already has real material in it. Say what it will add first |

### `wipe_sample_workspace`

_Remove the sample search_

Take the sample back out. Removes ONLY what load_sample_workspace wrote, from the list it recorded; anything the person has since edited or added to is KEPT, named in the report and left in place, as is a sample company still holding an application they kept. What it deletes is permanent — nothing goes to the archive — so say roughly what will go and get a plain yes. Returns what was deleted, what was kept and WHY, and `complete`: false means pieces are still held and the report names each, so read it back rather than reporting success. Calling it again picks up where it stopped.

**Overwrites or deletes.**

No arguments.

### `restart_tour`

_Show the welcome tour again_

Queue the web app's welcome tour to run again the next time this person opens it — the short walk through what the board, Me and the assistant connection are for. Reach for it when somebody says they are lost, that they never saw an introduction, or that they want the tutorial back; also worth offering to someone whose `whoami` shows tourSeenAt null who is clearly struggling. It does not open anything on its own — nothing here can reach into their browser — so say plainly that it will appear next time they load the app. Setting it back to seen is the tour's own job, not a tool: they put it away by finishing or closing it.

No arguments.

### `list_changes`

_What each assistant changed_

Every write that arrived over MCP, newest first: which connection, which tool, what it touched, and a line saying so. Reach for it when somebody asks what an assistant actually did, when something looks wrong and nobody remembers changing it, or before restore_revision with change_id so you can name the change. Saves made in the app's own screens are NOT listed, though they are still versioned. `undoable` and `restorePointAt` matter most: only writes replacing a resume or a role are versioned, and `restorePointAt` — where the record would go back to — is often EARLIER than the change, because versions coalesce within ten minutes per author. Say that time out loud before undoing ('back to 14:02, before three edits') and get a yes. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `connection_id` | string | Only changes made through this connection, from list_connections |
| `tool` | string | Only calls of this tool, e.g. 'update_resume' |
| `kind` | string | Only changes to this sort of thing: resume, role, application, contact, offer… |
| `record_id` | string | Only changes to this one record |
| `limit` | number | How many to return. Default 50, ceiling 500. |

### `list_revisions`

_Earlier versions of a resume or a role_

Every stored version of one resume or one role, newest first, with when it was taken and who caused it. Each row is a BEFORE image — the record as it was before a write replaced it — so the newest row is where an undo lands. Reach for it before update_resume or update_role on something that matters, to tell them what they could get back to, and after a write that went wrong. Versions are taken when the whole record is replaced, and when a role's background is appended to — not for a font or a rename — and COALESCED to one per record per author per ten minutes, keeping the older image. At most twenty are kept per record and old ones are swept, so this is a safety net, not an archive. `recordExists` false means the record was deleted and nothing can be restored to it. For a role, each row's `changedSince` lists the background lines added and removed since — exactly what restoring would undo; read those out first. Read-only.

| Argument | Type | |
| --- | --- | --- |
| `kind` | enum | **required** — Which sort of record. These are the only two that are versioned.  `RESUME` · `ROLE` |
| `record_id` | string | **required** — The resume id or the role id |
| `limit` | number | How many versions to return. Default and ceiling 20. |

### `restore_revision`

_Put a stored version back_

Replace a resume's document, or a role's fields, with an earlier stored version — or undo one change. Pass `id` (from list_revisions) when they can name the VERSION, or `change_id` (from list_changes, only writes it marks undoable) when they can name the CHANGE; it restores the version from just before that write. A deleted company, person or application comes back from the archive with restore_records; a deleted role or resume cannot come back at all. SAY WHAT WILL HAPPEN AND GET A YES FIRST: this replaces the current state, and because versions are coalesced within ten minutes per author, it can go back past several edits. The restore is itself undoable — the result names `redoRevisionId`. For a resume only the DOCUMENT comes back: template, font, size, margins and any published link stay as they are. `changed` false means the record already matched; say so rather than reporting work that did not happen. Refuses, writing nothing, when the stored version does not parse or the record is gone.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | Revision id, from list_revisions |
| `change_id` | string | Or a change id, from list_changes: undo that one write |

### `list_connections`

_List AI connections_

Every assistant wired to this workspace: what it is called, which client it was set up for, when it last called in and from what. Reach for it to answer 'which of these am I still using?' or before rotating something — the ids come back here. Tokens deliberately do not: they are credentials, they would sit in this transcript forever, and the only place a person needs to see one is the client they are pasting it into. `isThisOne` marks the connection you are calling through right now, and `scope` says what each one is SERVED — FULL is everything, and a narrowed one is offered fewer tools without being able to do less to the account. update_connection changes it.

No arguments.

### `create_connection`

_Connect another assistant_

Mint a new connection URL so a second client — the laptop's editor, a phone app, a terminal — can reach this workspace too. Returns the URL and the exact steps for that client, so you can hand somebody a copy-paste answer to 'how do I add this to Cursor?'. Give every client its own rather than sharing one: that is what lets a single laptop be disconnected later without breaking everything else. The URL is a credential with full read and write over this person's career history, resumes and pipeline — say so when you hand it over, and never post it anywhere it will be stored.

| Argument | Type | |
| --- | --- | --- |
| `client` | string | Which client it is for: claude \| claude-code \| chatgpt \| cursor \| vscode \| windsurf \| generic-http \| stdio-bridge \| raw. Sets the setup steps returned. |
| `name` | string | What to call it in the list, e.g. 'Cursor — work laptop'. Defaults to the client's name. |

### `update_connection`

_Rename a connection, or narrow what it is served_

Rename one connection, change what it is served, or both. `name` is for the person — 'Cursor — old laptop' makes it obvious later which one to revoke. `scope` sets which tools that client is offered: FULL is everything; WRITING is Me, resumes and letters plus the four reads a document needs about its job; PIPELINE is the search — applications, people, the archive, mail and calendar; READONLY is every tool that writes nothing. Narrowing is a ROUTING AID, NOT A PERMISSION: the URL still reaches the whole account, anyone who can sign in can widen it again, and it is never a reason to hand a connection URL to somebody you would not hand the account to. What it buys is accuracy — a client choosing from sixty tools picks wrong less often than one choosing from two hundred. It applies on the client's next call; one that caches its tool list may need reconnecting. Say which connection and which scope before calling, because a narrowed client silently loses abilities its person may be relying on. Ids come from list_connections, which shows each one's current scope.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Connection id, from list_connections |
| `name` | string | The new name |
| `scope` | enum | FULL, WRITING, PIPELINE or READONLY  `FULL` · `WRITING` · `PIPELINE` · `READONLY` |

### `rotate_connection`

_Issue a new token for a connection_

Kill a connection's URL and issue a fresh one on the same row, keeping its name and place in the list. This is the answer to 'I sold that laptop' or 'I pasted the URL in a chat by mistake' — the old address stops working the moment this returns, and nothing else is affected. It also means the client that was using it goes dark until somebody pastes the new URL in, so say that before doing it. Returns the new URL; treat it like the password it is.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Connection id, from list_connections |

### `get_capture_link`

_The link that captures a posting from a phone_

The private address that turns a job posting into an application without opening the app, plus the bookmarklet built around it — the answer to 'I find jobs on my phone'. Tap the bookmark on a posting and the job lands on the wishlist. Returns the URL, the bookmarklet, how many postings it has captured and when it was last used — or `exists` false when none has been minted, the default. THE URL IS A CREDENTIAL: anyone holding it can add applications here. It can read nothing, but never repeat it anywhere it will be stored; they can copy it from Settings → Connections themselves. Read-only.

No arguments.

### `set_capture_link`

_Mint, rotate or revoke the capture link_

Create the capture link, replace it, or switch it off. Minting hands back the URL and the bookmarklet; MINTING WHEN ONE ALREADY EXISTS ROTATES IT, which kills the old URL immediately — every bookmark and Shortcut built on it stops working and has to be replaced, so only do it when they say the link has leaked or they want a new one. `off` true revokes it: the address goes back to answering 404 for everybody, and nothing already captured is touched. Tell them which of the three you are about to do, in those words, before you call it. The link is capped at thirty captures an hour, which is generous for a person and useless to anyone who found it, and it should never be pasted anywhere that unfurls links — a preview bot following it would fire it.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `off` | boolean | Revoke the link instead of minting one. Nothing already captured is affected |

### `delete_connection`

_Disconnect an assistant_

Remove a connection for good. Its URL stops working immediately and cannot be brought back — a replacement is a new connection with a new URL. Prefer rotate_connection when the client is still in use and only the URL has leaked. Check list_connections first: deleting the one you are calling through ends this session mid-conversation.

**Overwrites or deletes.**

| Argument | Type | |
| --- | --- | --- |
| `id` | string | **required** — Connection id, from list_connections |
